# E4 — evidence-stale

> **Disclaimer.** E4 compares declared date *metadata*, not the factual
> currency of evidence content. A benchmark report whose prose was
> corrected in 2025 but whose underlying data still comes from 2024 will
> show as "new" by its declared dates. E4 answers: *does the declared
> evidence date predate the Skill's declared baseline date?* It does not
> answer *is this evidence actually out of date?*

Severity: `info` (advisory, never blocks CI by default).

## What E4 checks

For each `(claim, local-path reference)` pair that the existing E1–E3
association step already links, E4:

1. Reads the referenced evidence file (bounded to 1 MiB, UTF-8-sig,
   root-confined, symlink-safe).
2. Extracts a **declared evidence date** using the source-group model.
3. Extracts a **declared skill date** from SKILL.md frontmatter.
4. Compares the two normalized UTC calendar dates. If the evidence date
   is **strictly earlier**, emits one info finding.

## Two different fallback policies (intentional)

* **Evidence side — conservative, group-dies-on-ambiguity.** Source groups
  are tried in order G1a (`as_of`, `data_date`) → G1b (`date`, `updated`,
  `last_updated`, `last_modified`, `generated`, `run_date`) → G2 (date in
  the filename) → G3 (labeled date line in content). If a group has any
  field present but all values are unparseable, or yields two different
  dates, E4 **silently skips** and does not fall through to a lower
  group.
* **Skill side — permissive first-parseable.** Fields are tried in
  priority order `date` → `updated` → `last_modified` → `version_date`.
  The first field that parses wins; an invalid value moves on to the next.

The asymmetry reflects that the author directly controls the Skill
frontmatter, while evidence files come from many sources.

## Supported date formats

After trimming whitespace, a value must match one of:

* `YYYY-MM-DD`, `YYYY/MM/DD`, `YYYY.MM.DD`
* ISO datetime with optional `Z` or `±HH:MM` offset:
  `YYYY-MM-DDTHH:MM[:SS]` with optional timezone
* Space-separated datetime: `YYYY-MM-DD HH:MM[:SS]` with optional timezone

Rejected silently: natural-language dates, two-digit years, relative
dates, month names, fractional seconds, calendar-impossible dates
(`2025-02-30`), timezone offsets outside `±14:00`, placeholders
(`YYYY-MM-DD`, `TODO`, `TBD`, `<date>`, `N/A`, `-`), and any year
before 2000.

Naive datetimes are treated as UTC. Dates without time are not
timezone-converted.

## Silent-skip conditions

E4 emits nothing when any of the following holds:

* Reference is a URL or a command (not a local path).
* Referenced path is missing, escapes the Skill root, or is a symlink
  escape.
* File extension is not in `.md .markdown .txt .json .yaml .yml .csv`.
* File exceeds 1 MiB, cannot be read, or is not valid UTF-8.
* No unique, parseable evidence date can be extracted (ambiguity,
  invalid value, no date anywhere).
* No parseable skill date exists in frontmatter.
* Evidence date equals or is later than the skill date.
* A wildcard reference matches multiple files (E7 reports the
  ambiguity; E4 does not pick).

## Examples

**Positive (E4 fires).**

```markdown
---
date: 2025-03-01
---
We reduced latency by 40% — see [benchmark](bench.md).
```

`bench.md`:

```markdown
---
date: 2024-06-15
---
```

Finding: `declared evidence date 2024-06-15 predates skill date 2025-03-01 by 259 days`.

**Negative (E4 silent).**

* `bench.md` has `date: 2025-04-01` (newer than the skill date).
* `bench.md` has no date anywhere and no date in its filename.
* `bench.md` has both `date: 2024-06-15` and `updated: 2025-02-01` (G1b
  group ambiguity — silent).
